01 · Foundation

A skill is a folder.
The folder is the skill.

The most common misconception: skills are "just markdown files." The most powerful ones are nothing like that. A skill is a folder — a composable workspace the agent can navigate, discover, and act on. That distinction changes how you design them.

The file system itself is a design surface. What you put in it — and how you point Claude toward it — determines what the skill can do. This is progressive disclosure: structure that reveals context on demand, not all at once.

my-analysis-skill/
├── SKILL.md                 # instructions + trigger description
├── references/
│   └── api.md               # detailed signatures — Claude reads when needed
├── assets/
│   └── report-template.md   # output template to copy and populate
├── scripts/
│   ├── fetch_events.py      # warehouse helpers with credentials baked in
│   └── cohort_utils.py      # reusable cohort logic for Claude to compose from
└── config.json              # setup state: env, warehouse, output channel

Notice that SKILL.md doesn't carry everything — it points to things. Claude reads references/api.md when it needs signatures. It picks up report-template.md when producing output. The scripts are there to compose from, not reconstruct. This is the folder doing the work.

For data scientists

Think of a skill like a project repo, not a README. It can carry your helper libraries, canonical query patterns, warehouse credentials, and analysis templates — all things Claude can discover and use without being told every time.

Progressive disclosure

You don't front-load everything into the main file. You structure what exists and tell Claude where to find it. Context is loaded on demand — which keeps your instructions lean and your skill adaptable.

Configuration options

Skills in Claude Code can register dynamic hooks, persist state across sessions, and compose with other installed skills. The teams getting the most out of skills use these options creatively — not just the instructions file.

The implication

Before you write a line of SKILL.md, think about the folder. What scripts, templates, or reference files could live here? What would Claude reach for if it knew they existed?

02 · Craft

Six principles for
writing great skills

Most skills start weak and compound in value over time. Every principle below addresses a specific way skills fail — and what right looks like instead.

1

Don't state the obvious

Claude already knows pandas, SQL, and how to write a data pipeline. Skill content that restates general knowledge wastes context and dilutes the signal. Focus exclusively on what Claude cannot know without you — your internal conventions, your canonical tables, the steps your team always gets wrong.

DS example — the difference 
✗  "Use pandas for dataframe operations and SQL for queries."
✓  "Never join on user_id before the dedup step in users_clean.
    Skipping it causes row explosion. This bites everyone at least once."
2

Build a Gotchas section — and keep building it

The highest-signal content in any skill is a ## Gotchas section at the bottom of SKILL.md. This isn't written once — it's a living log. The loop: run the skill, Claude hits a failure or produces a wrong result, you add that failure as a gotcha entry, repeat. Each entry should name the failure, explain why it happens, and state what to do instead. Over time this section becomes the most valuable part of the skill.

What it looks like in SKILL.md 
## Gotchas

- cohort_events uses UTC; users_clean uses local TZ.
  Always convert before joining or your cohorts will be off by hours.

- The `activated` flag is written asynchronously.
  Wait at least 15 minutes after signup before querying it.

- session_id is not unique across devices.
  Use the composite key (user_id, session_id) or results are wrong.
3

Use progressive disclosure across the file system

Don't collapse everything into SKILL.md. Split detailed function signatures into references/api.md. Put output templates in assets/. Put helper scripts in scripts/. Then tell Claude what files exist and when to reach for them — it will load that context on demand rather than all at once. This keeps your main instructions file readable and your skill composable.

Pattern in SKILL.md 
For full function signatures and usage examples,
see references/api.md.

When producing a report, copy and populate
the template at assets/report-template.md.
4

Write the description for the model, not for humans

When Claude Code starts a session it scans every installed skill's description to decide whether a skill applies to the current request. That makes the description a trigger condition, not a summary. A weak description causes undertriggering — Claude never reaches for the skill even when it would help. Write it as an explicit list of the situations that should invoke it.

Weak vs. strong trigger description 
✗  "Helper for data analysis tasks."

✓  "Use when the user wants to query funnel events, analyze cohort
    retention, compare segment conversion rates, investigate
    signup-to-activation drop-off, or explore event-level user data."
5

Don't railroad Claude

Claude follows the letter of your instructions — not the spirit. Overly prescriptive skills fail silently: Claude executes exactly what you wrote, even when the situation calls for something slightly different. The failure mode isn't an error — it's a subtly wrong result that looks plausible. Because skills are reused across many different requests, instructions that are too rigid will break on edge cases you didn't anticipate when you wrote them.

The failure mode, made concrete 
✗  "Always query the last 30 days."
    → User asks about last quarter. Claude queries 30 days anyway.

✓  "Default to the last 30 days unless the user specifies a range."
    → Claude adapts to the actual request.
6

Think through setup

Some skills need context before they can work correctly — which warehouse environment? which Slack channel for output? Rather than hardcoding these or silently guessing, have Claude ask once on first run and store the answers in a config.json inside the skill directory. Every subsequent run reads the config and skips setup entirely. This makes skills portable across team members without becoming rigid.

Setup pattern 
On first run: check for config.json — if missing, ask the user:
  "Which warehouse environment? (prod / staging)"
  "Which Slack channel for output?"

Store answers: { "warehouse": "prod", "channel": "#data-team" }

Subsequent runs: read config silently, skip setup entirely.
03 · Advanced Patterns

Four patterns that
raise the ceiling

These patterns unlock a different class of capability once you have the basics in place. Each solves a real problem in data science workflows that simpler skills can't address.

Hooks on demand

Session-scoped guardrails

Skills can register hooks that activate only when the skill is called and expire when the session ends. Useful for guardrails you don't want running all the time — but absolutely need when touching production data or running destructive operations.

/careful
# Blocks: DROP TABLE, DELETE FROM,
# rm -rf, force-push to main.
# Active only for this session —
# won't interfere with normal work.
Memory & state

Skills that remember across sessions

Skills can write and read persistent state that survives upgrades. Log every analysis run — next session, Claude reads its own history and knows what's already been explored, without you having to brief it again.

$CLAUDE_PLUGIN_DATA — the stable storage directory allocated per skill. Unlike the skill folder itself (wiped on upgrade), data written here persists. See docs → 
# analyses.log (append-only)
2025-03-17 | cohort Q1  | n=42k
2025-03-18 | funnel wk11| -12% act
# Next run: Claude diffs automatically
Scripts & helpers

Give Claude code to compose from

Embed helper libraries in scripts/ so Claude spends its turns on composition logic — deciding what to analyze and how — rather than reconstructing boilerplate from scratch. The richer your helpers, the more sophisticated the analysis it can produce on demand.

# scripts/fetch_events.py
def get_cohort(start, end, segment):
    # Credentials + standard filters
    # Canonical join logic baked in
    # Claude composes on top of this
Composing skills

Skills that invoke other skills

Reference other installed skills by name in your instructions. Claude will invoke them automatically, enabling multi-skill pipelines triggered by a single command. Dependency management is manual for now — document what your skill depends on explicitly.

PreToolUse — a hook that fires before any tool call, letting you intercept, log, or block specific actions. Used for measuring skill usage across a team. See docs → 
# notebook-report skill
# Depends on: funnel-query,
#   cohort-compare, grafana
# Claude chains them — one command,
# full pipeline output.
04 · Org Scale

From personal tool
to team infrastructure

A skill one person uses is useful. A skill the whole team uses compounds in value. Distribution, governance, and measurement are what bridge that gap.

Repo-checked skills

Check skills into .claude/skills/ in your repo. Everyone on the project gets them automatically on clone. Simple, zero-friction, works well for small teams with shared codebases.

Every checked-in skill adds to the model's context window. As your skill library grows, that cost compounds.

./.claude/skills/

Plugin marketplace

An internal marketplace where engineers publish skills and teammates install only what they need. Keeps context lean. Enables org-wide distribution without centralizing control or bloating every project.

Requires lightweight governance to avoid skill sprawl and redundancy.

Plugin marketplace docs →

Lightweight governance flow

Step 1 Build & sandbox in GitHub ›
Step 2 Share in Slack, invite use ›
Step 3 Wait for traction ›
Step 4 PR to marketplace

No central committee decides what gets in — traction decides. Skill owners are accountable for maintaining their own skills. A PreToolUse hook logging every invocation lets you see what's being used and what's undertriggering relative to expectations.

⚠

It's easy to create redundant or low-quality skills. A second pair of eyes on the description and gotchas section — before a skill reaches the marketplace — is the minimum viable curation step.
