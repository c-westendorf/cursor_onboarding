Why Most Agent Sessions Fail

The problems degrade productivity before you notice them.
01

Context Rot

With 200k token windows, agents forget earlier decisions, re-explore paths already tried, and lose coherence within the first hour of complex work. No memory across sessions means every day starts from zero.

Critical
02

Wasted Inference Cost

Using Opus for file searches, Grep for pattern matching, and MCPs for tasks that a CLI handles in 10 tokens — costs 10–20x more than necessary with no quality gain.

Critical
03

Repeated Mistakes

Claude makes an error, you correct it, same error appears two sessions later. Without a learning system, corrections don't persist. You're retraining on every session.

High
04

No Verification Loop

Code is written, assumed correct, and integrated — without automated checkpoints. Bugs accumulate. The agent has no eval harness to know when it's wrong.

High
05

Unscoped Delegation

Subagents with no tool restrictions, no model assignment, no output format. They return walls of text the orchestrator has to reparse, burning context and adding noise.

High
The Reality

Most people blame the model when sessions go wrong. The model is rarely the problem. The harness — the system of rules, memory, hooks, and delegation — is doing almost no work. That's the gap.

"Early on, I spent time building reusable workflows. Tedious to build, but this had a wild compounding effect as models and agent harnesses improved."
@omarsar0 — ML researcher
What changes

When you build the harness properly: sessions run for hours without context rot. Costs drop 60–80%. The agent learns from mistakes automatically. Code is verified before you see it.

The 4 Harness Primitives
RULES Always-follow .md files. The agent's non-negotiable operating standards — coding style, security, git conventions, testing requirements.

Using Opus for file search costs 20x more and returns the same answer. Model routing is the highest-leverage cost control available.

Context Window Budget

Your 200k window shrinks fast. Each MCP tool description costs tokens before any work starts. With too many MCPs active, effective context can drop to ~70k.

MCPs active ≤ 10 enabled
Tools active ≤ 80 tools
Autocompact at 50% (not 95%)
Thinking tokens 10,000 (not 32k)
The Haiku + Opus strategy

Sonnet sits at a 1.67× price difference from Opus — marginal for most. The real savings: Haiku at 5× cheaper than Opus for all "worker" tasks. Default to Sonnet, delegate to Haiku, escalate to Opus only when the first attempt fails or the task is architectural.

P2 · 03/18
Memory & Context

Every Session Starts From Zero — Unless You Build Memory

Without session persistence, corrections don't carry over. The agent relearns every mistake every day.
The 3-Hook Memory Lifecycle
🟢
SessionStart
Load last 7 days of session files. Inject previous context automatically.
💾
PreCompact
Before context compaction, save current state to session file.
🔴
Stop
On session end, persist learnings + summary to ~/.claude/sessions/
What session files contain

What worked

Verifiable decisions with evidence — approaches confirmed by tests passing

What failed

Approaches attempted but discarded, with the reason why

What's remaining

Incomplete tasks, next steps, blockers — the handoff for tomorrow

Key decisions

Architecture choices, trade-offs made, context for the next session

Strategic Compaction — not auto

Auto-compact fires at 95% context — often mid-implementation, losing variable names and partial state. Instead: compact after research (before coding), after a milestone (before next), after failed approach (before retry).

Never compact mid-implementation.
Dynamic system prompt injection

System prompt content has higher authority than user messages. Use --system-prompt for strict behavioral rules that must be prioritized.

alias cc-dev='claude --system-prompt \
  "$(cat ~/.claude/contexts/dev.md)"'
alias cc-review='claude --system-prompt \
  "$(cat ~/.claude/contexts/review.md)"'

Create a session-end memory hook
// ~/.claude/hooks/session-end.js  (Stop hook)
const fs = require('fs'), path = require('path');
let input = '';
process.stdin.on('data', d => input += d);
process.stdin.on('end', () => {
  const dir = path.join(process.env.HOME, '.claude', 'sessions');
  fs.mkdirSync(dir, { recursive: true });
  fs.writeFileSync(path.join(dir, Date.now() + '.json'),
    JSON.stringify(JSON.parse(input), null, 2));
});
  • Open ~/.claude/settings.json (create if missing) → add under the "hooks" key: "Stop": [{"matcher":"*","hooks":[{"type":"command","command":"node ~/.claude/hooks/session-end.js"}]}]
  • mkdir -p ~/.claude/sessions — session files will appear here after next session ends
  • Full 3-hook system → companion repo / hooks/

How to use session files mid-session

When hitting context limits: ask Claude to summarize current state into a new session file. Start a fresh conversation with @~/.claude/sessions/YYYY-MM-DD.tmp to resume exactly where you left off — without re-exploring.

Where this config goes

Paste the hook config at left into ~/.claude/settings.json under a top-level "hooks" key. Create the file if it doesn't exist — it's plain JSON.

{ "hooks": { "Stop": [...], "SessionStart": [...], "PreCompact": [...] } }
Common mistake — context pollution

Create a new session file each day. Never append old sessions into new work — stale context from failed approaches can steer the agent down the wrong path. One file per session, then prune older than 30 days.

P3 · 05/18
Continuous Learning

Make the Agent Learn From Its Own Mistakes

Every repeated correction is wasted tokens. Build the feedback loop that captures patterns automatically and persists them as reusable skills.
The Learning Loop
01 You correct the agent — a debugging fix, a workaround, a project-specific pattern
02 Stop hook fires at session end — evaluates session for non-trivial patterns worth saving
03 Pattern saved as instinct with confidence score → ~/.claude/skills/learned/
04 /evolve clusters related instincts into a full SKILL.md — auto-loaded next session
05 Same mistake never happens again — the fix is now part of the harness
Why Stop hook, not UserPromptSubmit

UserPromptSubmit fires on every message — adds latency to every prompt, runs piecemeal. Stop fires once at session end — evaluates the complete session, zero latency during work. Always use Stop for learning extraction.

Instinct lifecycle commands
/learn Extract pattern mid-session — run right after solving something non-trivial
/learn-eval Extract + score pattern quality before saving — prevents noise accumulation
/instinct-status View all learned instincts with confidence scores
/evolve Cluster related instincts into a named, reusable skill
/prune Delete expired pending instincts (30-day TTL) — keeps the skill set clean
/skill-create Generate skills from your git history — learns from what you've already shipped

P4 · 07/18
Subagent Orchestration

Delegate With Scope. Evaluate Every Return.

Subagents save context — but only if the orchestrator validates their output before accepting it. Summaries miss what they don't know to include.
The Sequential Phase Pipeline
01
Research
Explore agent gathers context, identifies patterns. Model: Haiku.
→ research-summary.md
02
Plan
Planner agent reads summary, creates implementation plan. Model: Sonnet.
→ plan.md
03
Implement
TDD guide agent reads plan, writes tests first, then code. Model: Sonnet.
→ code changes
04
Review
Code reviewer checks all changes for quality + security. Model: Opus.
→ review.md
05
Verify
Build resolver runs tests, fixes issues, loops back if needed. Model: Sonnet.
→ done / loop
The Iterative Retrieval Pattern

Subagents only know the literal query — not the PURPOSE behind it. Their summaries miss what they don't know to include.

1.Dispatch subagent with query and the objective (why you need it)
2.Orchestrator evaluates the return — is it sufficient?
3.If not: ask follow-up questions, send subagent back to source
4.Loop max 3 cycles — prevents infinite retrieval
Key orchestration rules

One input → one output per agent

Agents with multiple responsibilities blur scope and burn context

Outputs become file inputs

Store intermediate results in files — not just memory that compacts away

/clear between phases

Fresh context at each phase prevents cross-contamination from earlier exploration

P5 · 09/18
Verification & Evals

The Agent Should Know When It's Wrong Before You Do

Verification loops catch failures automatically. Evals measure improvement. Without both, you're debugging by hand at the end.
Checkpoint-Based

Set explicit verification gates between phases. Agent must pass before continuing. Best for linear workflows with clear milestones.

Task → Checkpoint → pass? → next
no? → fix → retry
Continuous

Run tests + lint after every major change. Report regressions immediately. Best for exploratory refactoring with no clear milestones.

Edit → auto-test → pass → continue
fail → stop & fix
pass@k vs pass^k — choose based on your need
Metrick=1k=3k=5Use when
pass@k 70% 91% 97% At least one attempt succeeds — OK for feature work
pass^k 70% 34% 17% All attempts must succeed — needed for consistency

Use pass@k when you need it to work. Use pass^k when consistency and determinism are essential.

Grader types (from Anthropic)

Code-based

String match, binary tests, static analysis. Fast, cheap, objective — brittle to valid variations.

Model-based

Rubric scoring, natural language assertions. Flexible, handles nuance — non-deterministic and more expensive.

Human

SME review, spot-check sampling. Gold standard — expensive and slow. Use for calibration only.

Benchmarking your skills

Fork a conversation → run the same task WITH and WITHOUT a skill in separate worktrees → pull up a diff → compare token usage and output quality. This is how you measure whether a skill is actually helping.

Add a PostToolUse auto-verify hook
#!/bin/bash
# ~/.claude/hooks/post-tool-verify.sh
INPUT=$(cat)
FILE=$(echo "$INPUT" | python3 -c   "import json,sys; print(json.load(sys.stdin).get('tool_input',{}).get('file_path',''))" 2>/dev/null)
[[ "$FILE" == *.ts ]] && npx tsc --noEmit && exit 0 || exit 2
[[ "$FILE" == *.py ]] && python -m pytest -q 2>&1 | tail -5 || exit 2
exit 0
  • Register: "PostToolUse": [{ "matcher": "Write|Edit", "command": "bash ~/.claude/hooks/post-tool-verify.sh" }]
  • Exit code 2 blocks Claude — it sees the error output and self-corrects
  • Full verification hook → companion repo / hooks/

        "type": "command",

      // Python: run tests after edit

More terminals ≠ more output. The goal is: how much can you achieve with the fewest instances? Add terminals only when you have a genuine, non-overlapping reason.
Proven parallel patterns

Main chat: code changes

One instance owns all file modifications. Never split code changes across instances without worktrees.

Fork: codebase questions

Run /fork for "how does X work?" exploration — no file writes, just reads and answers.

Fork: external research

Documentation scraping, GitHub searches, API reference — parallel to ongoing implementation.

Worktrees: overlapping work

When two instances MUST touch the same codebase — use git worktrees to isolate changes.

// ~/.claude/hooks/secret-scan.js  (UserPromptSubmit)
const PATTERNS = [/sk-[a-zA-Z0-9]{20,}/, /AKIA[0-9A-Z]{16}/,
  /ghp_[a-zA-Z0-9]{36}/, /password\s*[:=]\s*\S+/i];
let input = '';
process.stdin.on('data', d => input += d);
process.stdin.on('end', () => {
  const { prompt } = JSON.parse(input);
  if (PATTERNS.some(p => p.test(prompt))) {
    process.stderr.write('Secret detected — remove it and retry.
');
    process.exit(2); // blocks Claude
  }
});

~/.claude/hooks/secret-scan.js
// UserPromptSubmit hook — runs before Claude sees each message
// exit 2 = block the prompt; exit 0 = allow through
const SECRET_PATTERNS = [
  { pattern: /sk-[a-zA-Z0-9]{20,}/, label: 'OpenAI API key' },
  { pattern: /AKIA[0-9A-Z]{16}/, label: 'AWS access key' },
  { pattern: /ghp_[a-zA-Z0-9]{36}/, label: 'GitHub PAT' },
  { pattern: /gho_[a-zA-Z0-9]{36}/, label: 'GitHub OAuth token' },
  { pattern: /password\s*[:=]\s*["'][^"']{4,}["']/i, label: 'Inline password' },
  { pattern: /-----BEGIN.*PRIVATE KEY-----/, label: 'Private key' },
];
let input = '';
process.stdin.on('data', chunk => { input += chunk; });
process.stdin.on('end', () => {
  const { prompt = '' } = JSON.parse(input);
  for (const { pattern, label } of SECRET_PATTERNS) {
    if (pattern.test(prompt)) {
      process.stderr.write(`⚠️  Secret detected: ${label}\nRemove before sending.\n`);
      process.exit(2); // block
    }
  }
  process.exit(0); // allow
});

Start Here. Graduate When Ready.

Tier 1 patterns have a low skill floor and high return. Master these before Tier 2. Most experienced practitioners use Tier 1 for 80% of their work.
Tier 1 — Start Here

Low skill floor · High return · Build these first

Each of these is a direct force multiplier with minimal setup overhead

Subagents

Direct buff for preventing context rot and ad-hoc specialization. Half the complexity of multi-agent, half the risk, still major gains. Start here before any parallelization.

Metaprompting (planning first)

"I take 3 minutes to prompt a 20-minute task." Direct buff — improves first-attempt success rates and sanity-checks assumptions before any code is written.

Rules + Hooks (structured primitives)

Always-follow standards and trigger-based automations. Install once, benefit on every session indefinitely. Lowest effort, highest compound return.

Memory persistence

Session state files + 3 lifecycle hooks. Eliminates starting from zero each day. Most impactful change for daily productivity after rules/hooks.

Tier 2 — Graduate Here

High skill floor · High variance · Only when needed

High upside but easy to misapply. Don't start here.

Long-running agents

Need to understand the shape of a 15-min vs 4-hour task. Takes significant trial-and-error to calibrate. Only useful once Tier 1 is solid.

Parallel multi-agent

Very high variance — only useful on highly complex or well-segmented tasks. "If 2 tasks take 10 min and you spend time merging, it's counterproductive."

Role-based multi-agent

Models evolve too fast for hard-coded role heuristics unless the arbitrage is very high. Hard to test, easy to over-engineer.

Computer use agents

Very early paradigm. Requires significant wrangling. Useful in narrow scenarios — don't make it a default workflow pattern yet.

The graduation test

You're ready for Tier 2 when: Tier 1 is fully installed and running smoothly, you have a specific use case that Tier 1 can't address, and you can clearly define the scope boundaries that prevent parallel instances from interfering.
